# 本机管道设计 · 设计说明（消息 → 本机执行 → 回执）

> 落盘 2026-11-17。这份文档说清：为什么最终选了"本机 Named Pipe 管道"这条路（而不是平台定时/邮箱轮询）、整条链怎么走、三段代码各干什么、指令与二次确认怎么设计、安全边界在哪、已知限制是什么。
>
> 这份是可编辑文档，后续改指令集/确认机制/配置项，改这里对应段落再动代码。

---

## 0. 一句话说清管道是什么

一个常驻在本机的 Windows Named Pipe 服务（`\\.\pipe\job-hunt-workbench-inbox`）。你（或任何本机进程）往管道写一行 JSON 指令，服务解析后调用本机 8787 任务总线，回执从同一条连接返回。**不依赖平台定时任务、不依赖邮箱登录、不依赖外网。** 形态和 bsk daemon 一样，但只在本机闭环。

---

## 1. 为什么是本机管道（选型过程，值得记）

用户原始诉求："服务做通讯，问询、说什么东西，让它随时看我那边有没有发的消息，然后到这边来执行。" 三种方案评估过：

| 方案 | 为什么没选 / 怎么选 |
|---|---|
| **平台定时自动化**（RRULE 每 2 分钟轮询邮箱） | ❌ 平台 RRULE 只接受**单个** BYHOUR/BYMINUTE，无法做到"每 2 分钟"；且要求电脑开机+WorkBuddy 常驻。技术上被平台限制挡死。 |
| **bsk 浏览器扩展 + 邮箱网页** | ❌ 扩展协议 1.8 < daemon 1.9，`read` 不可用；QQ 邮箱网页当时未登录；中文 URL 在 bsk 里编码异常 404。bsk 最终只承担浏览器操作，不承担消息层。 |
| **Agent Mail 中继**（一个转发别名地址） | ⚠️ 可读可发，`inbox_bridge.js` 也能接，但**没有创建任何定时自动化**——缺一个"定时去读"的触发器，等于半条路。 |
| **本机 Named Pipe** | ✅ 用户明确要"像 bsk 那种本机管道"。零依赖、常驻本机、即时、无凭据上网风险。**最终采用。** |

关键判断：**不虚构后台能力**。WorkBuddy 原生常驻监听消息未证实，官方 Create-Task 只明确 UI 创建任务，本机 PATH 未找到 workbuddy/codebuddy 命令。所以没有假装"接通了后台监听"，而是做成"本机管道 + 会话手动/自动取件"的可验证链路。

## 2. 架构与数据流

```
                         ┌─────────────────────────────────────┐
   你 / 本机脚本          │  本机 Named Pipe                     │
   node pipe_client.js ──► \\.\pipe\job-hunt-workbench-inbox   │
   "分析 active"          │  （pipe_bridge.js 常驻监听）         │
                         └──────────────┬──────────────────────┘
                                        │ 一行 JSON：{id,token,command}
                                        ▼
                     ┌──────────────────────────────────────────┐
                     │ pipe_bridge.js                           │
                     │  · 令牌校验 / 去重 / 串行队列             │
                     │  · 把 command 包成 {from,subject,body}   │
                     └──────────────┬───────────────────────────┘
                                    │ ib.execute(msg, cfg, st)
                                    ▼
                     ┌──────────────────────────────────────────┐
                     │ inbox_bridge.js                          │
                     │  · 解析指令 / 确认码 / HTTP 调任务总线    │
                     └──────────────┬───────────────────────────┘
                                    │ http.request POST /api/job
                                    ▼
                     ┌──────────────────────────────────────────┐
                     │ server.js :8787  →  job_bus.js           │
                     │  · script 类：本机 spawn 执行             │
                     │  · agent 类：pending，等 WorkBuddy 取件   │
                     └──────────────┬───────────────────────────┘
                                    │ 回执沿原连接返回 + 写 log/reply_log
                                    ▼
                          pipe_client.js 打印回执
                          （CONFIRM_CODE / JOB_ID）
```

**一条连接、一次往返**：客户端写一行 JSON，服务端在同一连接上写一行回执 JSON。管道是本机内核对象，外部网络无法直连。

## 3. 配置（`config/local/pipe_bridge.json` · gitignored）

键结构（token 值已脱敏）：

```json
{
  "schema": "pipe/v1",
  "enabled": true,
  "token": "<本地凭据，gitignored>",
  "sender": "pipe://local",
  "pipe_name": "\\\\.\\pipe\\job-hunt-workbench-inbox",
  "api_base": "http://127.0.0.1:8787",
  "state_file": "jobs/pipe_bridge_state.json",
  "log_file": "jobs/pipe_bridge.log",
  "reply_log": "jobs/pipe_replies.jsonl",
  "confirm_ttl_minutes": 30,
  "reply_prefix": "[管道]",
  "token_hint": "管道客户端已自动携带凭据，指令直接写",
  "allow_delivery": true
}
```

模板在 `config/pipe_bridge.example.json`（Public 轨，占位值）。**代码里不设默认文件名**：`cfg()` 读不到文件直接 `throw`，缺 `token/sender/pipe_name/api_base/state_file` 任一就报错退出——猜错文件名会写坏数据，所以宁可不启动。

启动方式：
- `启动管道服务.bat`（双击，保持窗口打开即服务存活）
- 或 `node pipe_bridge.js`

## 4. 三段代码逐段说明

### 4.1 `pipe_client.js`（客户端，发指令）

```js
const id = Date.now().toString(36) + '-' + crypto.randomBytes(3).toString('hex');
const payload = JSON.stringify({ id: id, token: c.token, command: command }) + '\n';
const socket = net.connect(c.pipe_name, () => { socket.write(payload); });
```

- 每次生成唯一 `id`（时间戳+随机），供服务端去重。
- 自动从本地配置读 token 附上——所以用户发指令时**不用手写令牌**。
- 收到回执后：打印 `res.reply`，若是 `deliver_request` 额外打印 `CONFIRM_CODE=`，若有任务额外打印 `JOB_ID=`。

用法：
```bash
node pipe_client.js "状态"
node pipe_client.js "分析 active"
node pipe_client.js "投递 delivery-fde.json max=2"     # 只发确认码
node pipe_client.js "CONFIRM <确认码>"                   # 二次确认才真投
```

### 4.2 `pipe_bridge.js`（管道服务端，常驻）

**串行队列**——避免多条指令并发改同一份 state：
```js
let queue = Promise.resolve();
// 每读到一行，串到队列尾部
queue = queue.then(() => handle(line, c, st)).then(res => {
  if(!socket.destroyed) socket.write(JSON.stringify(res) + '\n');
});
```

**`handle()` 四道关**：
```js
if(req.token !== c.token) return { ok:false, error:'BAD_TOKEN' };          // 1 令牌
if((st.seen||[]).indexOf(id) >= 0) return { action:'duplicate', reply:'' }; // 2 去重
const msg = { id, from:c.sender, subject:c.token+' '+command, body:'' };
let out = await ib.execute(msg, c, st);                                    // 3 复用解析
st.seen = (st.seen||[]).concat([id]).slice(-1000);  saveState(c, st);       // 4 留痕
```

设计要点：
- **解析逻辑全部复用 `inbox_bridge.js`**，不写第二套口径（"指令怎么解析、确认码怎么发"只在一处定义）。
- `state` 用 `tmp + rename` 原子写，避免写一半崩了留下半个文件。
- 去重队列保留最近 1000 条 id。
- 每条回执同时写 `log_file` 和 `reply_log`（append-only）。

### 4.3 `inbox_bridge.js`（指令解析与确认码核心）

这是整套最有安全价值的文件，被管道服务直接复用。

**指令解析 `parseCommand()`**——只认这些：
| 指令 | 动作 |
|---|---|
| `状态` / `status` | 列最近 10 条任务 |
| `任务 <id>` / `job <id>` | 查单任务状态+日志尾 |
| `分析 [active\|all]` | 建 `position-analysis` 脚本任务 |
| `检查 <条件名>` | 建 `jkit-check` |
| `试跑 <条件名> [max=N] [budget=N]` | 建 `jkit-dry-run`
| `投递 <条件名> [max=N]` | **只发确认码，不真投** |
| `CONFIRM <码>` | 二次确认后才真投 |
| `帮助` / `help` | 指令帮助 |

解析时先去掉令牌、去标点、取首行，正则匹配；无法识别的参数直接报"无法识别"，不猜。

**二次确认闸**（真实投递必须两步）：
```js
// 第一步：投递请求 → 生成一次性码，存 state
const code = crypto.randomBytes(4).toString('hex').toUpperCase();   // 8 位大写
st.confirms[code] = {
  params: a.params,
  from: normEmail(msg.from),
  expires_at: Date.now() + (c.confirm_ttl_minutes||30)*60000        // 默认 30 分钟
};
// 第二步：CONFIRM → 三校验后删码、建真投任务
if(!e)                  return reject('确认码不存在或已使用');
if(e.from !== from)     return reject('确认码发件人不匹配');
if(Date.now() > e.expires_at){ delete ...; return reject('确认码已过期'); }
delete st.confirms[a.code];                                          // 一次有效
api(c, '/api/job', 'POST', { kind:'jkit-deliver',
     params: Object.assign({}, e.params, { confirm:true }) });
```

**为什么必须两步**：真实投递是不可逆的外部动作（点真按钮、发真招呼）。一次性码 + 发件人绑定 + 30 分钟过期 + 用完即删，四层保证"误发指令/重放/过期"都不会误投。而且 `job_bus.create` 里对 `jkit-deliver` 还有第三道：`if(def.needsConfirm && params.confirm!==true) return err`——即使绕过管道直接调 API，没有 `confirm:true` 也建不了真投任务。

令牌/白名单：`authorize()` 校验 `allowed_senders` 白名单 + 文本里含 token。管道模式里 `sender=pipe://local`、token 由客户端自动带，等价于"只有本机持有配置的人能发"。

## 5. 与任务总线的接口

管道最终都落到 `POST /api/job`（见 `job_bus.js`）：

| kind | runner | 执行方 |
|---|---|---|
| `jkit-check` / `jkit-inspect` | script | job_bus 本机 spawn |
| `jkit-dry-run` / `jkit-deliver` | script | job_bus 本机 spawn（真投需 confirm） |
| `position-analysis` | script | job_bus 本机 spawn |
| `position-deep-analysis` / `track-sync` / `market-research` 等 | **agent** | pending，等 WorkBuddy 会话取件 |

回执里 `job_id` 让你能追到 `GET /api/job/<id>` 看执行结果与日志。script 类秒级完成，agent 类要等会话取件。

## 6. 安全边界小结

1. **令牌**：每条指令必须带本地 token，错令牌 `BAD_TOKEN` 拒绝。
2. **去重**：id 去重，重放指令返回 `duplicate`、不重复执行。
3. **二次确认**：真实投递必须 `投递` 拿码 → `CONFIRM <码>`，码一次有效、绑发件人、30 分钟过期。
4. **双重闸门**：管道侧确认码 + job_bus 侧 `needsConfirm`，绕过管道也建不了真投。
5. **本机限定**：Named Pipe 是本机内核对象，外部网络连不上；token 与所有 state 都在 gitignored 的 `config/local/` 和 `jobs/`。
6. **原子写**：state 用 `tmp+rename`，不写坏文件。
7. **测试覆盖**：`tests/test_inbox_bridge.js`（Node 2 项）覆盖错发件人、错码、重放；投递前必须真判出 dry-run 条目的闸门另有回归测试。

## 7. 已知限制（读文档时必须带着）

- **不保活**：两个后台进程（8787 server.js、pipe_bridge.js）随会话启动，**会话结束可能停止**。下次用双击 `启动招聘服务.bat` + `启动管道服务.bat`，或改开机自启。bsk daemon 同理，真投/联网调研前先 `bsk browsers` 探活。
- **agent 取件=手工触发（契约见 §9）**：管道能把 agent 任务建起来，但"WorkBuddy 会话去取件执行"**明确采用手工触发**——不假设有常驻监听。点按钮/发指令建 `pending` 任务 → 你在会话里复制指令执行 → `POST /api/job/:id/result` 回写。这条链已可靠闭环（含产物落盘与时间线回显）。
- **真实投递已实跑成功**：2026-11-17 首次真投成功（AI Agent开发工程师 84.0/A、AI产品助理 65/B）；daemon 曾在会话切换后掉线导致"没有已连接的浏览器"，拉起后恢复。
- **Windows 专属**：Named Pipe 路径 `\\.\pipe\...` 是 Windows 语法，换系统要改管道实现。

## 9. 执行契约：手工触发 + 可靠回写（2026-11-17 定稿）

### 9.1 为什么是手工触发，不打通自动取件
WorkBuddy 的"常驻后台监听消息并自动执行"能力**未证实**（官方只明确 UI 建任务，本机 PATH 无 workbuddy/codebuddy 命令）。不虚构后台能力，所以明确采用手工触发契约：

```
页面点按钮 / 管道发指令
   → POST /api/job {kind, params, command_text, command_source}  建 pending 任务
   → 工作台「任务指令」面板出现该任务，可一键复制完整执行指令
   → 你把指令粘进 WorkBuddy 会话，会话按 SOP 执行（联网调研 / 深析 / 面试材料 / 跟踪抓取）
   → 会话结束时 POST /api/job/:id/result 回写结果 + ai_writes
   → 任务转 done，工作台时间线立即显示；刷新不丢
```

**为什么这样设计**：
- agent 类任务 `runner:'agent'`，任务总线只排队、不执行（`job_bus.js` 的 BUILTIN）。
- 回写后状态从 `pending` → `done`（`submitResult`），**不会卡在 running**——`recover()` 只处理 `status==='running'` 的脚本任务，agent 的 pending 不受影响。
- 幂等去重：同 kind + 同 params 的 pending/running 任务不会重复建，避免连点建多条。

### 9.2 回写接口的完整契约（`POST /api/job/:id/result`）
回写体（WorkBuddy 会话按 SOP 产出后调用）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `ok` | bool | 默认 true；false 则任务转 failed |
| `summary` | string | 一句话结论，页面时间线顶部显示 |
| `data` | object | 结构化结果（如深析结论、track-daily/v1） |
| `artifacts` | string[] | 产物相对路径（可选） |
| `reply_text` | string | 回执原文（逐字保存，页面可展开） |
| `ai_writes` | object[] | AI 对工作台的写入留痕，逐条 `{target,before,after,at}` |
| `log` | string | 追加到 `jobs/<id>.log` |

**硬约束**：`ai_writes` 每条的 target/before/after 都夹紧长度、最多 100 条，不落整份隐私数据；回写是 append 语义，原始 `request.md` 不可变。

### 9.3 交互持久化四件套（P3）
一次任务对应 `workbuddy_out/interactions/<job_id>/` 下四份不可变产物：

| 文件 | 何时写 | 内容 |
|---|---|---|
| `request.md` | `create()` | 指令原文 + 来源 + 时间（逐字，绝不改写） |
| `response.md` | `submitResult()` | 回执原文 |
| `result.json` | `submitResult()` | 结构化结果 |
| `writes.jsonl` | `submitResult()` | AI 写入 diff，一行一条 |

索引层在 `jobs/<id>.json` 增加 5 个字段：`command_text` / `command_source` / `reply_text` / `result_artifacts` / `ai_writes`。

**读取接口**（只读）：
- `GET /api/interactions?kind=&with_command=1&limit=` → 时间线列表（指令→回执→结果→写入，按 kind 过滤）
- `GET /api/interactions/:id` → 单条详情 + 四件套全文

**验收**：任意一次按钮/管道指令，刷新后在工作台「任务指令 → 执行记录」能看到完整链路，指令原文与提交时逐字一致。

**实跑验证（2026-11-17 14:41）**：建一条 `position-deep-analysis` 任务带 `command_text` + `command_source:"pipe"` →
`request.md` 逐字落盘；回写 `reply_text` + `result` + 1 条 `ai_writes` → 四件套齐全；
`GET /api/interactions/:id` 读回原文逐字一致、回执/结果/写入均可查。前端 `工作台.html` 任务抽屉已挂时间线（按 kind 过滤 + 点开看四段），刷新不丢。
