## 1. 系统分层

```
┌─────────────────────────────────────────────────────────────┐
│  浏览器端                                                     │
│  工作台.html（壳：侧栏导航 + 视图条 + iframe + 任务指令抽屉）    │
│    ├─ 工作台-首页.html          数据总览                       │
│    ├─ 工作台-定位.html          ① 岗位判断与分析（画像/分析/详情）│
│    ├─ 工作台-投递条件.html      ② 投递条件（L0-L4/试跑/真投）    │
│    ├─ 工作台-投递台账.html      投递事件流只读                  │
│    └─ app.html         ③ 跟踪与回复（唯一可写主表）     │
└───────────────────────┬─────────────────────────────────────┘
                        │ HTTP（同源 8787）
┌───────────────────────▼─────────────────────────────────────┐
│  server.js（8787，零依赖 Node）                              │
│    ├─ workbench_readonly.js  只读聚合：routes/ledger/families  │
│    ├─ job_bus.js             任务总线：建任务/回写/时间线       │
│    ├─ conditions_api.js      投递条件读写（白名单+留档）        │
│    ├─ atlas_api.js           图谱结构化索引（就地展开）         │
│    └─ /api/profile /api/data 画像与跟踪主表写入                │
└───────┬──────────────────────────┬──────────────────────────┘
        │ spawn python             │ Named Pipe
┌───────▼────────────┐   ┌─────────▼──────────────────────────┐
│  jkit（Python）     │   │ pipe_bridge → inbox_bridge           │
│  analyze 分析       │   │ 本机消息 → 解析指令 → 建任务 → 回执   │
│  apply   投递       │   └────────────────────────────────────┘
│  score   判定       │
│  searchfeed 采集    │   ┌────────────────────────────────────┐
└───────┬────────────┘   │ WorkBuddy 会话（手工触发 agent 任务） │
        │                │ 深析/联网调研/面试材料/跟踪抓取 → 回写 │
┌───────▼─────────────────────────────────────────────────────┐
│  磁盘持久化（唯一真相）                                        │
│  config/local/*.json · data/ledger.json(+CSV) · runs/*/ledger │
│  jobs/<id>.json + workbuddy_out/interactions/<id>/ 四件套      │
└─────────────────────────────────────────────────────────────┘
```

**核心设计原则**：页面**只展示 + 只发指令**，从不自己算分析结果、从不直接调 AI。所有智能判断由 WorkBuddy 会话承担，结果落盘后页面回显。

## 2. 两条执行路径

系统里有两类任务（`job_bus.js` 的 `runner` 字段），页面用同一套轮询接口，不感知区别：

| 路径 | runner | 谁执行 | 典型任务 | 回写方式 |
|---|---|---|---|---|
| **脚本类** | `script` | 本进程 spawn python | 分析、试跑、真投、校验条件 | 子进程退出自动写 done/failed |
| **智能体类** | `agent` | WorkBuddy 会话手工取件 | 深析、联网调研、面试材料、跟踪抓取 | 会话调 `POST /api/job/:id/result` 回写 |

**agent 是手工触发**（契约见 `系统说明-02 §9`）：WorkBuddy 常驻自动取件能力未证实，不虚构。流程是"点按钮建 pending 任务 → 任务面板复制指令 → 粘进 WorkBuddy 会话执行 → 回写 → 时间线显示"。

## 3. 六条关键数据流

### 3.1 画像 → 分析 → 方向推荐
1. `工作台-定位.html`「我是谁」表单 → `POST /api/profile` 写 `config/local/profile.json`（写前留档到 `runs/backup/`）。
2. 点「开始分析」→ `POST /api/job {kind:'position-analysis'}` → job_bus spawn `python -m jkit analyze`。
3. analyze 读 `profile.json` × 市场快照（`族匹配数据` 等）→ 算 5 维匹配分 → 结果落 `jobs/<id>.result.json`。
4. 页面轮询 `GET /api/job/:id` 拿到 result，渲染推荐表；点行就地展开图谱详情（`/api/atlas?family=`）。

### 3.2 委托 WorkBuddy 深析（真实分析）
1. 点「交给 WorkBuddy 深析」→ 建 `position-deep-analysis` agent 任务（带可选 note）。
2. 任务面板显示指令 → 用户复制到 WorkBuddy 会话 → 会话按 `templates/workbuddy/tasks/position_deep_analysis.example.md` SOP 取只读接口数据、联网核查、产出结论。
3. 会话回写 `POST /api/job/:id/result`（summary/data/reply_text/ai_writes）→ 任务转 done。
4. 交互四件套落盘 + 时间线可回看（刷新不丢）。

### 3.3 投递条件：编辑 → 生效 → 执行
1. `工作台-投递条件.html` 读 `GET /api/conditions` 展示六份条件；L0 筛选等可改 → `PUT /api/conditions` 白名单写回 `config/local/conditions/<slug>.json`（写前留档）。
2. **条件每次运行实时读盘**（`load_conditions`），不建快照；`deliver.max`/`budget_min` 是数量与预算的唯一来源（P-A：页面不填就不传 CLI 参数覆盖）。
3. 点试跑/真投 → job_bus spawn `jkit apply` → 详情二次校验 → 投够 N 条或候选耗尽停止。
4. 每批 `summary.json` 记本次实际条件 + target/completed/shortfall，台账页可查。

### 3.4 投递执行：筛选 → 逐卡判定 → 投递（正确性闭环）
`jkit/apply.py` 的硬顺序：落地 → 平台原生筛选 → 逐搜索词翻页 → 卡片层粗筛 → 开面板读详情 → 详情层 `score.judge` 全字段判定 → 投递 → 留在此页 → 下一条。
- **数量闭环**（P-C）：只 `delivered` 计数，投够 N 停；候选耗尽标 `exhausted`。
- **详情校验**（P-D）：判定用详情字段而非卡片；失败原因（veto/reasons/hr_level/jd）入台账，可展开看。
- **安全阀**：冷却/超额零请求；风控/配额即时停；同公司只投一次。

### 3.5 跟踪与回复
`app.html` 是**唯一可写主表**（`data/ledger.json` + 2 CSV）。海投流水（`runs/*/ledger.jsonl`）不灌进主表，通过 `source_refs[]` 引用关联。"今日跟踪"面板是台账快照 + WorkBuddy 只读抓取（`track-sync` agent 任务，不改台账）。

### 3.6 执行记录：指令 → 回执 → 结果 → AI 写入（P3 持久化）
任意任务建/回写时，`job_bus.js` 落四件套到 `workbuddy_out/interactions/<id>/`：
- `request.md`（建任务时，指令原文逐字）
- `response.md` / `result.json` / `writes.jsonl`（回写时）
索引在 `jobs/<id>.json` 的 5 个字段；`GET /api/interactions` 供工作台任务面板时间线回显，刷新不丢。

## 4. 持久化清单（哪些数据在磁盘）

| 数据 | 文件 | 写入方 |
|---|---|---|
| 用户画像 | `config/local/profile.json` | `/api/profile` |
| 投递条件（6 份） | `config/local/conditions/*.json` | `/api/conditions` |
| 跟踪主表 | `data/ledger.json` + 2 CSV | `/api/data` |
| 投递事件流 | `runs/<id>/ledger.jsonl` + `summary.json` | `jkit apply` |
| 任务状态/结果 | `jobs/<id>.json` | job_bus |
| 交互四件套 | `workbuddy_out/interactions/<id>/` | job_bus |
| AI 分析产物 | `workbuddy_out/<类型>/` | WorkBuddy 会话（约定路径） |
| 导航/任务配置 | `config/local/routes.json` / `jobs.json` | 手工编辑 |

**易失、不持久化**：浏览器 localStorage（视图偏好、跨页 slug）、job_bus 的 running Map（进程内子进程表）。这些是 UI 状态，不是业务数据。

---

## 5. 两个数据模型（别混淆）

1. **跟踪台账**（`data/ledger.json`）：主应用读写，只留有沟通、有后续机会的重点记录。
2. **投递事件流**（`runs/<id>/ledger.jsonl`）：append-only 海投流水，只读聚合，不进主表。

首页"台账事件/已投递"读事件流；主应用读台账。两者通过 `source_refs[]` 关联，不是同一份数据。
