# 岗位判断 SOP · 设计说明（调研 → 判定 → 投递）

> 落盘 2026-11-17。这份文档说清"岗位判断"的三层结构：①**调研 SOP**（S0–S8，怎么把市场数据采回来）；②**单岗判定**（`score.py`，一条岗位到底投不投）；③**投递主链路**（`apply.py`，从落地到点按钮的 9 步顺序）。
>
> 这份是可编辑文档，后续改 veto 词表、打分权重、投递顺序，改这里对应段落再动代码。

---

## 0. 三层结构总览

| 层 | 解决什么 | 代码/SOP | 触发 |
|---|---|---|---|
| ① 调研 SOP | 市场数据怎么采、怎么算、怎么交付 | `docs/岗位调研SOP.md`（S0–S8） | 人工定期调研 |
| ② 单岗判定 | 这一条岗位投不投、几分、为什么 | `jkit/score.py:judge()` | 投递链路逐卡调用 |
| ③ 投递主链路 | 从落地到点按钮的完整顺序与安全阀 | `jkit/apply.py:run()` | 试跑 / 真实投递任务 |

三者关系：①产出的市场画像喂给"分析"（见文档 01）；②是③每一步调用的核心判定器；③把②的判定落到真实平台动作。**判定口径只在 `score.py` 一处定义**，平台适配层只负责把页面字段归一成 `JobRecord`。

## 1. 第一层 · 调研 SOP（S0–S8，闸门不过即停）

原文在 `docs/岗位调研SOP.md`，这里提炼骨架。

### 1.1 三条总原则

- **口径先行**：没有 `scope.json` 冻结口径，不发起任何采集。
- **证据闭环**：任何结论必须能下钻到 `平台 + job_id/URL + 原文片段 + captured_at + extractor_version`；读不到 = `unknown`，不推测。
- **只读旁路**：零投递、零沟通、零收藏，不改规则、不回改历史运行、不绕登录/滑块/签名。

### 1.2 八阶段与闸门

| 阶段 | 动作 | 闸门 |
|---|---|---|
| S0 口径冻结 | 写 `scope.json`：岗位族、平台、城市、搜索词、时间窗、**用户原话+确认时间** | G0：任一未定或 AI 脑补 → 停、反问 |
| S1 采集就绪 | 合规打勾 + 逐平台探活（列表/面板/JD/技能/薪资/时间） | G1：字段未实测 → 标 `unknown` |
| S2 试采 | 每平台先采 20 条，人工逐条核对原文 | G2：编造字段/原文对不上/触发验证 → 停该平台 |
| S3 正式采集 | 按词表等量采、限速、**逐条即时写盘** | G3：样本不足/占比失衡 → 补采或分层出报告 |
| S4 归一结构化 | 去重、族归一、抽技能分必备/加分/仅提及、每项挂 `evidence_span` | G4：抽检 20 条可下钻原文 |
| S5 指标计算 | 五组指标（技术栈/要求/在招量/门槛/薪资）+ 匹配侧 | G5：可由 raw 独立复算；HR 活跃度**不进**匹配度 |
| S6 报告偏差声明 | 首页写清口径与已知偏差，明说"这是平台广告量，不是市场空缺总量" | G6：负责人确认偏差声明 |
| S7 下游交付 | 四份版本化契约，带 `source_snapshot_id` + `extractor_version` | G7：字段校验通过 |
| S8 复盘回流 | 新词进待审区；改 lane 需新建 condition + 批准 | G8：未批准只留建议，不改系统 |

### 1.3 一页式执行清单

```
① 冻结 scope.json（含原话+确认时间）→ G0
② 探活回填 platform_status.json + 合规打勾 → G1
③ 每平台试采 20 条，人工核对原文 → G2
④ 等量采集，逐条 append、限速、异常即停 → G3
⑤ 去重→归一→结构化，抽检 20 条可下钻 → G4
⑥ 算五组指标并独立复算 → G5
⑦ 出报告 + 偏差声明，交负责人确认 → G6
⑧ 校验四份交付契约的版本与证据索引 → G7
⑨ 只留建议清单；改 lane 需新 run/新 condition + 批准 → G8
```

### 1.4 踩过的坑（写进 SOP 的条款）

- 服务端直取 BOSS JD 会被重定向登录页，必须在已登录浏览器内读。
- BOSS 同关键词两次加载卡片顺序不同，跨次样本**不得合并**。
- 卡片与 JD 矛盾是普遍规律（实测 6 条 JD 里 3 处矛盾），**S4 必须以 JD 为门槛判据**，卡片经验/学历只作召回层。
- 短时间高频访问会触发平台的 L1 访问限制；风控是实际代价，冷却期必须硬停。

## 2. 第二层 · 单岗判定 `jkit/score.py:judge()`

### 2.1 先 veto（硬否决，一票否决，顺序即优先级）

按顺序命中任一即返回 C 档、不投：

1. **标题词 veto** `VETO_TITLE`：实习/兼职/日结、销售/客服/招生/猎头、硬件/嵌入式/机械、财务/酒店/生产工艺方向、推广/招聘/行政/人事、视频/短剧/运营/营销/内容、外贸/教师/设计 等。
2. **计薪方式**：`元/天`、`元/时` 否决。
3. **学历超纲**：岗位要求学历 > 我的学历（本科）否决（硕/博/MBA）。
4. **真外包**：`client_company` 非空否决。
5. **JD 隐性坑** `VETO_JD`：车间轮岗、外包、培训费、押金、异地 base、长期出差。
6. **经验门槛**：岗位最低要求 ≥ 我的年限+上限（默认 0+3）且 > 我的年限 → 否决（1-3 年可投，3-5 年否决）。
7. **行业黑名单**：只在"公司名+行业+融资+标题"上匹配，**不看 JD 正文**（JD 写"服务医疗客户"是业务范围，不等于医疗公司）。
8. **方向白名单**：标题必须落在 AI/技术/产品/售前售后，融资管培生、结构工程师这类即使互联网公司也不投。
9. **junior 纯职能**：助理族若标签全是 HR/行政/财务词且无任何技术信号 → 否决（防止 HR 助理被当技术助理投）。
10. **薪资下限**：`salary_floor` 启用时，低于下限否决（当前为 null，未启用）。

### 2.2 再五维打分（满分 100）

```
方向 40 + 门槛余量 25 + 公司质量 20 + 待遇 10 + 应届友好 5
A ≥ 70 ｜ B ≥ 55 ｜ C < 55
投递线 min_grade=B → A/B 投，C 不投
```

**关键设计：方向词表按岗位族路由**（`FAMILY_TABLES`）——这是踩坑换来的：

```python
FAMILY_TABLES = {
    "product": PRODUCT,          # 产品经理：需求/PRD/竞品/指标/解决方案
    "delivery": DELIVERY,        # 交付FDE：SUPPORT ∪ PRODUCT 并集取大
    "tech_support": SUPPORT,     # 技术支持：排障/工单/SLA/驻场/系统维护
    "project_mgmt": PM,          # 项目经理：进度/里程碑/风险/跨部门/验收
}
# 其余族（开发类）回落到 TECH: vue/react/springboot/docker/langchain/rag/mcp...
```

**为什么分表**：产品岗 JD 几乎没有 Vue/Docker，用开发栈打分会把"AI产品经理（多模态Agent方向）"压到 40 分 C 档；技术支持岗用开发栈会把"IT技术支持"压到 31 分。真正该看的是"这个岗位要什么证据"，不是"我会什么"。`job_family_of()` 的分类顺序（junior > project_mgmt > delivery > product > tech_support > ai_dev > other）也是踩出来的，注释里写明了每一对先后理由。

### 2.3 `judge()` 的输出 `Verdict`

```python
Verdict(score, grade, deliverable, veto, job_family, reasons, detail)
```

- `veto`：非空 = 被否决，含原因（如 `行业:医疗`、`经验要3-5年`）；
- `deliverable`：是否进投递队列（由 `min_grade` 决定）；
- `detail`：五维分项 + 技能命中 + 经验/学历/公司规模/投递线，逐项可解释。

### 2.4 条件从哪来

阈值不写死在代码：`Conditions` 从 `config/local/conditions/<slug>.json` 载入（学历、年限、薪资下限、投递等级线、行业黑白名单、方向白名单），`judge()` 只按它判。代码里只保留**词表**（哪些是硬否决、哪些技能值多少分）——因为那是平台无关的常识，不是用户筛选条件。

6 份条件：`ai-pm / delivery-fde / it-support / presales / tech-assistant / tech-support`，各自通过 `profile_ref` 引用共享画像，只保留各族真正不同的字段（搜索词、薪资下限、投放节奏）。

## 3. 第三层 · 投递主链路 `jkit/apply.py:run()`

### 3.1 九步顺序（硬约束，不能换）

```
1. land()            整页加载 1 次（只带城市）
2. apply_filters()   ★ 先套平台原生筛选，失败即停
3. search(q)         页面内换词
4. read_cards()      读这一页的卡
5. 卡片层判定        标题/学历/经验本地就能判的先淘汰，省掉开面板
6. 点卡读面板        右侧面板换过去（不跳详情页）
7. 详情层判定        score.judge()，全字段
8. 投递              面板就在眼前，点按钮；弹窗点"留在此页"
9. 下一张
```

**为什么第 2 步必须在第 4 步前**：不做原生筛选就是在全量结果里逐条开面板。一个词 30 张卡，20 张注定不投（学历/经验不符），先筛掉省 2/3 面板读取——是时间，也是风控面。

**为什么不"先读完全部详情再统一投"**：那样要花几十秒读十几条 JD 才发现只有四条能投。正确顺序是"进一个、判一个、能投当场投、马上进下一个"，中途被杀只丢一条不丢一批。

### 3.2 三道准入门槛（详情层之前）

在 `score.judge` 之前还有三道 policy 门槛（`jkit/policy.py`）：

1. **今日在线 + 能回复**：`REQUIRE_TODAY_ONLINE`，只有 `hr_online=True` 或 `active_days==0` 放行；智联有回复信号直接当"今日在线+能回复"；BOSS 无回复字段，退回"今日在线"代理并**如实标注**。
2. **JD 真实需求**：`MIN_JD_LEN`，JD 太短 = 挂着不招/凑数，淘汰。
3. 外包已由 `score` 的 `client_company` 硬否决处理，不重复。

### 3.3 安全阀（`jkit/guard.py`）

挂在 driver 上的 `on_request = g.note_request`，**每次导航都计数**：

- `preflight()`：冷却期/超额时**零请求退出**；
- `Budget(minutes, target)`：时间预算，剩余少时自动放慢节奏系数；
- `Humanizer`：dwell/gap/rest 拟人节奏，避免机器特征；
- 触发风控 → `g.trip()` 写冷却，本轮立即停、**不重试**；
- 连续 5 次单卡失败 → 停轮。

### 3.4 去重策略（踩坑修正过的）

```python
done = set(store.delivered_index(ws))   # 只用真实成功记录跨轮去重
settled = set()                          # 本轮防重
```

**不再用无版本的跨轮 settled 历史跳过**——旧逻辑里试跑/旧条件的淘汰记录会阻断随后真投，导致真投按钮全空。现在试跑的淘汰不会污染真投。跳过的卡也写台账行 + 原因（历史已判/已投过），不再静默跳过让人以为筛选坏了。

### 3.5 dry-run 与真投的闸门

- **真投软闸门（2026-11-17 改）**：真投按钮**始终可点**，点一下即可走真投链路。试跑结果只作为"参考信息"显示在按钮旁的状态区（如"最近试跑 0 条可投"），**既不阻断、也不再暗示必须先试跑**。以前是硬闸门（试跑没判出 `dry_run` 就禁用按钮），因用户要求"点击后能真投、试跑可选"改为软提示 + 并列交互：动作区真投在前、试跑在后，试跑条数可在 `试跑条数` 输入框自己定（默认 8，范围 1–200，不再写死 20）。真投仍保留两道安全：①页面连点两次确认（8 秒内）；②job_bus 的 `needsConfirm`（`jkit-deliver` 必须带 `confirm:true`）。另有"重判已判过的岗位"（`--recheck`），试跑与真投都透传，可在 0 可投时重判历史岗位。
- **同公司只投一次**：`delivered_companies` 集合，本轮同公司第二条跳过。
- **真投二次确认**：见文档 02——管道侧确认码 + job_bus 侧 `needsConfirm` 双闸。

### 3.6 台账数据契约

每条判定/投递都写一行 `runs/<run_id>/ledger.jsonl`（append-only），字段固定便于统计复盘：

```json
{
  "at": "ISO时间", "run_id": "...", "condition_id": "cond-xxx", "platform": "boss",
  "job_id": "...", "title": "...", "company": "...", "salary": "...",
  "exp": "...", "edu": "...", "city": "...", "company_scale": "...",
  "score": 71.5, "grade": "A", "job_family": "delivery", "deliverable": true,
  "veto": "", "reasons": [...], "detail": {...},
  "outcome": "delivered | dry_run | drop | skip | stop | already",
  "evidence": "判定依据/淘汰原因", "hr_level": "在线/今日回复/...",
  "jd_len": 1234, "jd_brief": "JD前400字", "job_snapshot": {...}
}
```

**两份数据模型别混淆**：跟踪台账 = `app.files.data`（主应用读写，有沟通的重点记录）；投递事件流 = `runs/<run_id>/ledger.jsonl`（append-only 海投流水，只读聚合）。

## 4. 已知问题（读文档时必须带着）

- **搜索词召回问题（未解决）**：搜「IT技术支持」在 BOSS 召回 15 张卡，14 张历史已判、1 张是「糖尿病护士（包住）」。**这是搜索词与平台召回的问题，不是评分逻辑**——veto 会正确挡掉护士岗，但有效新岗位太少。需要单独调搜索词或按公司行业过滤，别把 UI 当解。
- **卡片与 JD 矛盾**：以 JD 为门槛判据，卡片只作召回层。
- **活跃度不进匹配度**：HR 活跃度是"能不能投"的门槛，不是"匹配多好"的分数，两者不同量纲。
- **真投链路已验证**：一次真实投递成功后，日志会出现 `✓ delivered`「已向BOSS发送消息」，同时 `runs/<run_id>/ledger.jsonl` 追加 `outcome=delivered`。只看到「点了按钮」不算成功，要看这两处。
- **真投失败的头号原因：浏览器守护进程没起**。`bsk browsers` 探测不到已连接浏览器时，任务会秒级退出并报「没有已连接的浏览器」——**这不是条件 / 登录 / 判定的问题**。守护进程不随会话保活，每次开工前先探活，没起就先把它拉起来，能探到浏览器实例即恢复。
- **搜索词召回仍偏差**：`ai-pm` 方向搜「AI项目经理」等召回大量短剧/销售/教师/主播岗（veto 正确挡掉），靠「AI Agent开发工程师」等词才命中对口岗。`delivery-fde` 试跑 15 条、`it-support` 1 条曾全淘汰（销售/机器人/7K低于8K下限等）——**这是搜索词与召回/条件的问题，不是按钮或评分的问题**，要真投出岗需先调搜索词或放宽薪资下限等条件。
